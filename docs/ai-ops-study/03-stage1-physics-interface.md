## 2. Token：计费与截断的物理单位

### 2.1 定义

- **Token**：模型读写文本的离散单位（≈ 英文 ~4 字符 / 中文常更「贵」每字）
- **Input tokens**：系统提示 + 历史 + 工具结果 + 用户输入
- **Output tokens**：模型生成；通常单价更高
- **Context window**：单次请求可同时看见的 token 上限（含输入+输出预算）

### 2.2 控制流（一次 Chat Completion）

```text
Client
  -> 组装 messages[] / tools[] / 参数(temperature, max_tokens, ...)
  -> HTTPS POST /v1/chat/completions （或厂商等价接口）
  -> Gateway（鉴权、配额、路由、审计）
  -> Model Runtime（分词 -> 前向 -> 采样 -> 流式/整包返回）
  -> 响应 usage{prompt_tokens, completion_tokens, total_tokens}
```

运维视角检查点：

- 鉴权与租户配额（类似 API Gateway + ResourceQuota）
- 超时 / 重试 / 幂等键（流式场景尤其危险）
- 截断策略：超窗时谁负责裁剪（客户端 vs 网关 vs 模型侧）

### 2.3 与容量规划的类比

| LLM | 你熟悉的系统 |
|-----|--------------|
| context window | 单请求最大 payload / 连接缓冲 |
| tokens/min 限额 | QPS / 带宽配额 |
| GPU 显存 + KV cache | 内存水位与连接态 |
| TTFT / TPOT | P50/P99 延迟分位 |

## 3. 无状态 API：会话是你的责任

多数厂商 Chat API **服务端不持久化对话状态**（除非显式用 Assistants/Threads 类产品）。

含义：

1. 每轮必须回传完整需要的历史（或摘要）
2. 「记忆」落在：客户端、业务 DB、向量库、或会话存储
3. 排障时先问：**状态存在哪一层？TTL？一致性？**

最小状态机（生产可用）：

```text
session_id
  -> messages_store (append-only)
  -> compaction_policy (摘要 / 滑动窗 / 关键消息置顶)
  -> retrieval (按需注入 RAG 片段)
  -> call model (无状态)
  -> append assistant message + usage 计量
```

## 4. 幻觉边界：失败模式分类

把「胡说」拆成可观测类别（方便写告警与评测）：

| 类别 | 症状 | 典型缓解 |
|------|------|----------|
| 事实幻觉 | 编造 API/版本/命令 | RAG + 引用强制；工具验真 |
| 指令漂移 | 忽略约束/格式 | 结构化输出 + 校验器 |
| 工具幻觉 | 假装调用了工具 | 真实 tool loop；禁止口头宣称 |
| 越权幻觉 | 声称有权限执行变更 | 人工门禁 + 最小权限沙箱 |
| 过度自信 | 高确定性断言 | 强制不确定性表述 / 二次检索 |

运维落地：**幻觉不是「道德问题」，是依赖可靠性问题** —— 用熔断、人工门、金丝雀评测集处理。

## 6. 私有化引子（0.5 天，非完整 Stage 6）

企业转向私有/本地部署的四驱动力：

1. **合规与数据驻留**：日志、代码、客户数据不出域
2. **安全边界**：工具调用落在内网沙箱
3. **成本曲线**：高 QPS 长上下文时，API 单价可能劣于自建
4. **可控性**：模型版本钉死、变更窗口、回滚、审计

当前工作假设（见背景档案）：「KM」≈ 可私有部署的开源/国内模型族。

立刻可做（侧轨 P 起步）：`side-tracks/P-private-deploy.md`
