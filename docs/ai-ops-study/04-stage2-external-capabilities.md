# Stage 2 · 外部能力：组织知识库（RAG）与工具总线（MCP）

> 承接 Stage 1：模型只在窗口内做「分词 → 前向 → 采样」。  
> 本 Stage：把**组织要长期记住的**与**组织允许它动手的**接到模型外面。

## 框架对齐

| 常见说法 | 在本框架中的升格 |
|----------|------------------|
| RAG | 组织知识库：检索 + 权限 + 记忆治理 |
| Tools / Function Calling | 平台工具总线（以 MCP 为当代形态） |
| 插件 | 受鉴权/审计/沙箱约束的受管能力 |

北极星含义：外部能力不是聊天彩蛋，而是 AI 原生组织的两条腿——**记忆**与**行动**。

---

## 1. 为什么必须外置

Stage 1 已说明：上下文有限、API 无状态、采样无验真。因此：

1. 组织规程、复盘、配置真相 → 不能只靠模型参数「背住」
2. 查集群、开工单、跑脚本 → 不能靠模型「嘴上执行」

外部能力 = 给无状态推理引擎接上 **可读的组织记忆** 与 **可审计的行动出口**。

---

## 2. RAG → 组织知识库

### 2.1 最小数据流

```text
查询（用户问题 / Agent 子问题）
  → 鉴权（谁能看哪些知识域）
  → 检索（关键词 / 向量 / 混合）
  → 重排与截断（塞进窗口的预算）
  → 组装 prompt（引用块 + 约束：无依据勿断言）
  → 模型生成
  → （可选）引用校验 / 拒答
```

### 2.2 知识分层（对接侧轨 O）

| 层 | 例子 | 读 | 写 |
|----|------|----|----|
| 公开 Runbook | 排障 SOP | 广 | Curator |
| 内部架构 | 服务依赖图 | 岗位相关 | 架构主责 |
| 敏感 | 客户数据、密钥位置 | 禁止进提示词 | —；只经工具沙箱触达 |
| 变更审计 | 历史变更单 | Oncall+ | 系统追加，不可由模型改写 |

### 2.3 平台要点（轴 C）

- **权限先于相似度**：向量近 ≠ 有权读
- **新鲜度**：索引构建、失效、版本钉扎
- **引用契约**：回答必须能指回 chunk/文档 id
- **成本**：检索召回过大 → prompt_tokens 爆炸（回到 Stage 1 物理层）

### 2.4 失败模式

| 模式 | 表现 | 治理 |
|------|------|------|
| 检索落空仍硬答 | 事实幻觉 | 无命中则拒答或澄清 |
| 越权召回 | 泄密 | ACL 在检索层强制 |
| 过期文档 | 错误操作建议 | 有效期 / owner / 评审态 |
| 上下文塞爆 | 延迟与费用升 | 重排、摘要、分层引用 |

## 3. MCP / Tools → 平台工具总线

### 3.1 角色

模型负责「决定要不要调用、填什么参数」；**真正执行在工具运行时**。MCP（Model Context Protocol）把「工具发现、描述、调用」标准化，便于平台统一管控——它是总线形态，不是唯一实现。

### 3.2 控制流

```text
模型输出 tool_call(name, args)
  → 总线：鉴权 / 参数校验 / 策略（环境、角色）
  → 执行器：沙箱或受控后端
  → 结果（成功/失败/超时）写回 messages
  → 模型再次前向（看到工具结果后再说话）
```

没有这条闭环，就会出现 Stage 1 的 **工具幻觉**（嘴上说做了）。

### 3.3 与网关/运维同构

| 工具总线 | 你熟悉的平台能力 |
|----------|------------------|
| 工具注册表 | 服务目录 |
| 鉴权与角色 | RBAC / Admission |
| 沙箱 | 容器隔离、网络策略 |
| 超时重试 | 客户端策略 |
| 审计日志 | 变更与访问审计 |
| 限流熔断 | 依赖保护 |

### 3.4 危险分级（为 Stage 3 门禁铺路）

| 级 | 例子 | 默认策略 |
|----|------|----------|
| L0 只读探测 | 查文档、metrics 只读 | 可自动 |
| L1 只读生产查询 | kubectl get/describe/logs | 自动但强审计 |
| L2 写变更 | apply、重启、扩缩容 | **人工批准** |
| L3 不可逆 | 删库、清数据、密钥导出 | 默认拒绝或双人 |

## 4. RAG 与工具如何配合

典型值班路径：

```text
告警
  → RAG：拉匹配 Runbook 与历史复盘
  → 工具：只读探测验证假设
  → 模型：汇总现象/假设/证据
  → （Stage 3）若需变更 → 审批门 → 写工具
```

记忆提供「该怎么做的组织共识」；工具提供「现在系统真实状态」。缺一不可。

---

## 5. 与前后 Stage 的接口

- 上承 Stage 1：窗口预算、无状态会话、幻觉分类，全部仍生效  
- 下接 Stage 3：角色、审批、Harness 把工具 L2+ 与 SOP 编成可执行闭环  
- 侧轨 O：知识边界表 = RAG ACL 的规格来源  
- 侧轨 P / Stage 6：私有模型仍走同一知识库与工具总线（换的是推理后端）

## 6. 本 Stage 心智模型（一句话）

**模型是窗口内的推理引擎；RAG 是受权限约束的组织记忆；MCP/工具是受沙箱与审计约束的行动总线。**
